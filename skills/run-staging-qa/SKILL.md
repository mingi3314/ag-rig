# 스테이징 QA 실행

## 준비와 검증

- 기준 `.feature`, 대상 URL·배포 범위, 계정·테스트 데이터를 확인한다. 브라우징은 설치된 `ego-browser` 스킬을 읽고 따른다. 실제 주문·결제·외부 발송은 승인 범위 안에서만 수행한다.
- 미정 기준과 준비할 수 없는 조건은 실행 전에 식별하고, 가능한 핵심 검증부터 진행한다. 시간 제한에는 탐색·정리도 고려한다.
- 초기 조건에 도달했음을 확인한 뒤 명시된 행동과 기대 결과를 검증한다. 비동기 결과는 완료·실패 신호를 기다린다. 다른 타이밍·일부 경로의 결과로 전체 케이스를 판정하지 말고 분리해 기록한다. `Examples`의 각 행도 별도 케이스로 추적한다.
- 새 근거로 초안의 조건·행동·기대가 잘못됐음을 알면 사유를 남겨 정정한다. 실제 오동작을 정상으로 바꾸는 수정과 구분하고, 바뀐 케이스는 기존 증거가 충족하는 범위까지만 판정한다.

| 결과 | 기준 |
| --- | --- |
| PASS | 기대 결과를 모두 확인함 |
| FAIL | 조건이 충족된 상태에서 기대와 다른 동작을 관찰함 |
| BLOCKED | 준비·접근·관찰 수단 부족이나 미정 기준으로 검증을 완료할 수 없음 |
| NOT_RUN | 시간·범위 제한 등으로 실행하지 않음 |

오류로 후속 케이스가 막히면 오류와 차단을 구분한다. 필요한 만큼 재현하며 최초 관찰과 재시도 결과를 남긴다. 상태 변경의 성공 여부가 불명확하면 현재 상태부터 확인해 재실행을 결정한다.

## 탐색과 사용성

- 대상 사용자·작업·확인할 위험을 정하고, 관찰에 따라 입력·상태·순서·타이밍을 바꿔 의심을 좁힌다. 저장→재열기→수정 같은 연속 사용 중에는 매 행동 사이에 초기화하지 않는다. 범위·시간 안에서 의미 있는 변형을 살피고 반복 탐색은 마친다.
- 대표 사용자 작업을 처음부터 끝까지 수행하며 다음 행동을 찾거나 결과를 이해하고 실수를 복구하기 어려운 지점을 살핀다. 결과 내용도 요청 조건·근거 데이터와 대조한다. 상태 피드백, 용어, 통제, 반복 부담, 도움 등 [Jakob Nielsen의 원칙](https://www.nngroup.com/articles/ten-usability-heuristics/)을 단서로 삼되 작업의 제약과 대안을 고려한다.
- 기능 오류·사용성 개선·확인 필요 항목을 구분하고 같은 현상은 묶는다. 사용성은 관찰 사실 → 예상 작업 영향 → 개선 방향으로 설명한다. 원칙 위반이나 개인 취향만으로 결함을 확정하지 않는다.

## 리포트

지정한 출력 위치나 전달받은 실행 폴더를 사용하고, 둘 다 없으면 OS 임시 디렉터리에 고유한 `feature-qa-*` 실행 폴더를 만든다. 기본 리포트는 `report.html`로 저장하고 `.feature`와 `evidence/`를 링크한다. 외부 서비스 없이 열리는 HTML로 만들고, 화면 증거와 접히는 상세 기록을 제공한다. 기록의 입력·응답·로그는 HTML로 실행되지 않게 텍스트로 넣는다.

- **먼저 읽을 내용:** 중요한 발견·사용자 영향·다음 조치를 짧은 목록이나 표로 쓴다. 문제가 없으면 주요 검증 결과를 적는다. 판단을 바꾸는 미검증 사항은 해당 결론 가까이에 두고, 건수는 보조 정보로 사용한다.
- **발견 상세:** 문제를 드러내는 짧은 제목, 재현 조건·최소 절차, 기대 근거·실제 결과, 영향·우선순위 이유와 증거를 적는다. 사용성 개선과 확인 필요 항목도 작업 영향이 드러나게 쓴다.
- **검증 상세·부록:** 미실행을 포함한 케이스별 상태·기대·실제 결과와 집계, 탐색한 흐름과 남은 질문, 핵심 미검증 위험과 필요한 준비를 남긴다. 시각·URL·버전·역할·화면 환경·데이터 정리는 재현에 필요한 정보만 뒤에 모은다.

익숙하고 쉬운 말로 관찰·영향·다음 할 일을 짧게 연결한다. ‘재진입’은 ‘다시 열기’처럼 풀어 쓰고, 정확한 개발 용어·수치·식별자는 필요한 설명과 함께 상세 기록에 둔다. 긴 검증 표·환경 정보는 접어두고, 도구 사용·지침 준수 선언·작성 경위·반복 면책 문구는 덜어낸다.
맥락으로 알 수 있는 내용은 되풀이하지 않고, 제목·버튼·펼침 문구는 ‘더보기’, ‘실행 환경’처럼 짧고 익숙하게 쓴다.

우선순위는 영향·우회 가능성·반복 부담·발생 빈도의 근거로 설명한다. 재현 횟수를 실제 사용자 빈도로 간주하지 말고, 판단의 확실성과 심각도를 구분한다. 증거는 핵심 입력·상태와 현상 전후를 판별할 수 있게 남긴다.

응답에는 리포트 링크, 주요 결과·버그·사용성 개선과 남은 검증 범위를 요약한다.
