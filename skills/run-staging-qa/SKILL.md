# 스테이징 QA 실행

## 준비와 검증

- 기준 `.feature`, 대상 URL·배포 범위, 계정·테스트 데이터를 확인한다. 브라우징은 설치된 `ego-browser` 스킬을 읽고 따른다. 실제 주문·결제·외부 발송은 승인 범위 안에서만 수행한다.
- 핵심 규칙과 위험을 우선 검증하고, 시간 제한에는 탐색·정리도 고려한다. 시나리오의 기대 결과를 실제 동작에 맞춰 고치지 않는다.
- 케이스별 초기 조건을 준비하고 행동 후 모든 기대 결과를 관찰한다. 비동기 결과는 완료·실패 신호를 기다린다. `Examples`의 각 행을 별도 케이스로 추적하고 다음처럼 판정한다.

| 결과 | 기준 |
| --- | --- |
| PASS | 기대 결과를 모두 확인함 |
| FAIL | 조건이 충족된 상태에서 기대와 다른 동작을 관찰함 |
| BLOCKED | 준비·접근·관찰 수단 부족이나 미정 기준으로 검증을 완료할 수 없음 |
| NOT_RUN | 시간·범위 제한 등으로 실행하지 않음 |

오류로 후속 케이스가 막히면 오류와 차단을 구분한다. 필요한 만큼 재현하며 최초 관찰과 재시도 결과를 남긴다. 상태 변경의 성공 여부가 불명확하면 현재 상태부터 확인해 재실행을 결정한다.

## 탐색과 사용성

- 대상 사용자·작업·확인할 위험을 정하고, 관찰에 따라 입력·상태·순서·타이밍을 바꿔 의심을 좁힌다. 저장→재열기→수정 같은 연속 사용 중에는 매 행동 사이에 초기화하지 않는다. 범위·시간 안에서 의미 있는 변형을 살피고 반복 탐색은 마친다.
- 사용성은 상태 피드백, 용어·다음 행동, 실수 예방·복구, 일관성·반복 부담, 중요 정보·도움을 살핀다. [Jakob Nielsen의 원칙](https://www.nngroup.com/articles/ten-usability-heuristics/)을 단서로 삼되 사용자·기기·작업의 제약과 대안을 고려한다.
- 기능 오류·사용성 개선·확인 필요 항목을 구분하고 같은 현상은 묶는다. 사용성은 관찰 사실 → 예상 작업 영향 → 개선 방향으로 설명한다. 원칙 위반이나 개인 취향만으로 결함을 확정하지 않는다.

## 리포트

실제 리포트와 증거를 지정 위치나 기존 QA 리포트 위치에 저장한다. 기본 위치는 `qa/runs/<YYYYMMDD-HHmmss>/report.md`이며 이전 실행 기록은 보존한다.

- **실행 맥락·범위:** 시각·시간대, URL, 확인한 버전·계정 역할·화면 환경, 기준 시나리오.
- **케이스 결과:** 미실행을 포함한 케이스별 상태·기대·실제 결과와 상태별 건수, 관련 발견과 증거 링크.
- **탐색·발견:** 탐색 목표와 주요 시도·관찰·후속 질문. 발견별 재현 조건·절차, 기대 근거 또는 작업 영향, 재현 여부와 우선순위 이유.
- **남은 위험:** 원래 목표·핵심 규칙과 수행 범위를 대조한 중요한 미검증 영역, 필요한 준비·다음 확인·남은 데이터 정리.

우선순위는 영향·우회 가능성·반복 부담·발생 빈도의 근거로 설명한다. 재현 횟수를 실제 사용자 빈도로 간주하지 말고, 판단의 확실성과 심각도를 구분한다. 증거는 핵심 입력·상태와 현상 전후를 판별할 수 있게 남긴다.

응답에는 리포트 링크, 주요 결과·버그·사용성 개선과 남은 검증 범위를 요약한다.
